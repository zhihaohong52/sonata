# Architectural review

The CLI boundary in `src/cli.ts` owns command selection, argument validation, exit-code mapping, and process-level error handling, while delegating behavior to `src/commands/*` and `src/mcp/server.ts`; `main()` is therefore an orchestrator rather than a domain layer, and `packageRoot()`, `invokedAsProgram()`, and `tailWaitSeconds()` are appropriately small seams for installation-path and parsing behavior. The boundary is somewhat split because CLI-specific policy is duplicated in the command implementations and in the usage text: `main()` knows which flags are required and how results are printed, while `cmdRun()`, `cmdTail()`, and `cmdApprove()` independently define the same operation contracts. This is workable for a small CLI, but a shared command option/result schema would keep human and MCP callers from drifting. `main()` also dynamically imports `log`, `verify`, and `mcp` handlers while statically importing other commands, an incidental split in module-loading responsibility rather than a functional problem.

Configuration in `src/config.ts` owns the canonical Sonata model: `parseConfig()` validates harness names, provider-qualified ids, role mappings, and run defaults; `configPath()` and `loadConfig()` implement the deliberately non-merging project-then-machine lookup; `generatedAgents()` is the single source of truth for the role/model product. This subsystem depends on `smol-toml`, filesystem existence, and `types.ts`-level role/model concepts, and is consumed by run, sync, doctor, init, and detection. The main responsibility split is between configuration validation and initialization/config serialization: `parseConfig()` validates the result, but the omitted writer/init code must independently preserve quoting, collision rules, and legacy-format migration. Likewise `KNOWN_HARNESSES`/`KNOWN_ROLES` and adapter registration are separate lists (`config.ts` versus `adapters/index.ts`), so adding a harness requires coordinated edits in two places despite the adapter boundary being intended as the extension point.

Environment discovery in `src/detect.ts` owns machine inspection for `init` and `doctor`: `parseOpenCodeRefs()`, `parsePiRefs()`, and the imported `parseCodexModels()`/`parseReasonixRefs()` turn provider output into `ModelRef`; `offerableProviders()` groups and filters picker rows; `detectOpenCode()`, `detectPi()`, `detectCodex()`, and `detectReasonix()` run bounded probes; and `staleAgents()`, `isSonataAgent()`, and `pruneAgents()` manage generated-agent hygiene. It depends on adapter parsing and `checkVersion()` from `commands/doctor.ts`, which is the clearest responsibility leak: generic environment detection imports a command module for version semantics, and doctor in turn imports detection. The OpenCode repair functions `disabledOpencodeAgents()` and `enableOpencodeAgent()` also write another tool's config from detection code; that is intentionally narrow and safety-motivated, but a dedicated integration/repair module would separate observation from mutation. Pi, Codex, and Reasonix discovery are structurally parallel yet retain harness-specific process behavior here and parsing in adapters, so the boundary is good but not perfectly uniform.

Normalization in `src/normalize.ts` is a focused pure presentation layer: `stripAnsi()` removes terminal escape sequences, `cleanPane()` removes blank and spinner-only lines, and `newLines()` performs suffix/prefix overlap diffing. It depends on no runtime subsystem and is used by `tail.ts` and `approve.ts`. Its ownership is appropriately narrow; the only adjacent concern is that `tail.ts` owns pane snapshots and event cursors while `normalize.ts` owns the diff algorithm, meaning the persistence policy and the pure comparison policy are split across files. That is a healthy split, provided `newLines()` remains explicitly a pane-snapshot diff rather than being reused for the accumulated event log, which `cmdTail()` correctly avoids.

Role composition in `src/roles.ts` owns loading a role prompt and constructing the instruction contract through `loadRole()` and `composeInstructions()`. It depends on filesystem role templates and accepts already-derived repository context, task text, and report path from `commands/run.ts`; it does not know about harnesses or tmux. The reporting contract is consequently centralized in composition, but it is also repeated in generated wrapper-agent markdown in `commands/sync.ts` and in the role/task reminder assembled by `composeInstructions()`. Those are two different audiences—foreign harness and Claude wrapper—but both encode completion/provenance expectations, so changes to the report protocol currently require coordinated edits. `run.ts` additionally owns `repoContext()`, including the 24,000-character cap and CLAUDE/AGENTS precedence, which is logically input composition and could live beside `composeInstructions()` if the project wants one instruction-pipeline owner.

Permission and settings policy is split between `src/settings.ts` and `src/mode.ts`. `settings.ts` owns JSON preservation and safe mutation through `readSettings()`, `writeSettings()`, `installHook()`, `uninstallHook()`, `modeHookPresent()`, `missingAllowEntries()`, and `allowSonataTools()`; it also defines the three MCP tool allow-list and registration helpers. `mode.ts` owns reading the hook-produced session file through `readPermissionMode()` and maps Claude’s `auto` alias to `acceptEdits`. The split follows storage versus interpretation, but the path-selection rule is duplicated conceptually: the hook writer, `readPermissionMode()`, and config resolution must all agree on project/global placement. Doctor further checks these files while `init` performs installation, so the policy is distributed across settings, mode, doctor, and init. A single session-policy module could own the locations, mode encoding, and allow-list facts, while retaining settings’ preservation primitives.

Run persistence in `src/store.ts` owns the `.sonata/runs/<id>` layout and all durable run artifacts: `createRun()`/`writeMeta()` create metadata, `readMeta()` reads it, `readExit()`/`readReport()`/`readAnsweredPrompt()` expose completion and prompt state, cursor/event helpers maintain incremental progress, and `listRuns()` enumerates runs. It depends only on filesystem operations and `RunMeta` from `types.ts`, which is a clean low-level boundary. The responsibility that appears split is lifecycle interpretation: store writes `answered-prompt`, `tail.ts` decides when it is stale and calls `clearAnsweredPrompt()`, and `approve.ts` records it. Store is correctly persistence-only, but the answered-prompt protocol is an implicit cross-file state machine with no named abstraction, making it easy for future prompt behavior to diverge. `RunMeta.canWriteReport` is also produced by adapters and interpreted by tail, so the type is the right seam but the semantic contract lives in comments rather than one policy function.

Tmux lifecycle in `src/tmux.ts` owns process-facing session primitives—`newSession()`, `runScript()`, `capturePane()`, `tryCapturePane()`, `sendKeys()`, `hasSession()`, `listSessions()`, `currentSession()`, and `killSession()`—while `src/watchdog.ts` owns the generated shell wrapper in `wrapWithTimeout()`. The two together implement the detached-session, pane-observation, process-group, and hard-timeout design. `watchdog.ts` necessarily embeds shell/job-control knowledge that adapters also embed in their generated scripts, especially interactive foreground behavior and report-triggered quitting in Codex and Reasonix. That is the largest responsibility split in the runtime: tmux owns transport, watchdog owns timeout, adapters own harness launch, but all three generate or depend on shell process semantics. A future launch-runner abstraction could centralize sentinel creation, foregrounding, and process-group cleanup while leaving each adapter to specify only harness invocation and interactive hooks. The current implementation is otherwise deliberately defensive: `tryCapturePane()` distinguishes tmux failure from an empty pane, and `wrapWithTimeout()` kills the process group rather than only the direct shell.

`src/commands/run.ts` is the launch coordinator. `cmdRun()` resolves config, validates the model key, reads the session mode and task, creates the run directory, composes instructions, asks the selected adapter for a `LaunchPlan`, writes `harness.sh` and the watchdog-wrapped `cmd.sh`, updates metadata, creates the tmux session, and starts the script. Its dependencies make the intended layering visible: config, adapter registry, store, roles, mode, tmux, and watchdog are all composed here. The main split is that `cmdRun()` owns the generic launch protocol while adapters own scripts and permission semantics; `LaunchPlan.canWriteReport` is the key contract that prevents read-only runs from being falsely degraded. The function records an initial `interactive: false` and later rewrites it from the plan, which is harmless but shows metadata creation and finalized launch metadata are separated; a two-phase `createRun()` API could make that transition explicit.

Completion and progress in `src/commands/tail.ts` form the central runtime state machine. Pure `decide()` gives completion precedence over stale prompt matches and distinguishes `PROGRESS`, `PAUSED`, `DONE`, and `STALLED`; `harnessOutput()` filters Sonata’s own launch echo; `cmdTail()` captures and normalizes panes, diffs against `pane.snapshot`, appends `events.jsonl`, advances the cursor, settles after an exit sentinel, reads model or adapter fallback reports, suppresses already-answered prompts, handles timeout/degraded semantics, writes final metadata, and appends `provenance()` from `cmdVerify()`. This is the subsystem with the most responsibilities: observation, persistence advancement, prompt deduplication, report selection, degradation policy, and finalization all live in one command. Its reuse by `cmdWait()` is excellent because it avoids a second state machine, but the report/degraded decision and pane/event persistence could eventually be extracted into a run-observer service. The current cross-file split with adapter prompt detection is necessary for harness knowledge, while the cross-file split with `verify.ts` means completion provenance depends on an after-the-fact validator.

`src/commands/wait.ts` and `src/commands/approve.ts` provide the MCP-oriented continuation protocol. `cmdWait()` wraps `cmdTail()` with a configured `dispatchWindowSeconds` deadline and introduces `RUNNING` as a transport result rather than a durable run state; this keeps MCP calls bounded without changing the underlying lifecycle. `cmdApprove()` reads metadata, resolves the adapter, checks session liveness, obtains adapter-specific yes/no key sequences, captures and records the prompt, and sends keys. Their ownership is appropriately thin, but approval semantics are divided among adapter `approveKeys`, adapter `describePrompt()`, `approve.ts` prompt recording, and `tail.ts` prompt suppression. That division is what currently permits stale prompt edge cases: the answer record stores rendered prompt text, while detection is recomputed from the whole pane. A prompt identity or adapter-owned acknowledgement protocol would consolidate this state and avoid treating textual equality as identity.

The operational commands in `src/commands/doctor.ts` and `src/commands/sync.ts` manage setup health and generated agents. `checkVersion()` and `cmdDoctor()` verify tmux, resolved config, stray config, stale agents, wrapper tool permissions, required OpenCode agents, MCP registration, permission-hook presence, adapter versions, and adapter health; it also repairs disabled OpenCode agents through detection helpers. `generatedAgents()` in `config.ts` and `agentMarkdown()`/`cmdSync()` in `sync.ts` generate the wrapper surface, while `staleAgents()` identifies safe-to-delete Sonata-owned files. The key split is that doctor knows the expected wrapper text and tool names, sync emits that text, and settings defines the allow-list, so wrapper protocol is represented in three modules. The design is intentionally conservative about stale files, but a shared wrapper-manifest module would let doctor validate a versioned schema instead of regexing markdown. Doctor’s current early return when config loading fails is sensible because later checks have no reliable model set.

The MCP boundary is cleanly divided across `src/mcp/protocol.ts`, `src/mcp/server.ts`, and `src/mcp/tools.ts`. `protocol.ts` owns pure JSON-RPC dispatch in `handle()` for `initialize`, `tools/list`, and `tools/call`; `server.ts` owns newline-delimited stdio transport in `serveMcp()`/`runMcpStdio()` and optional debug/progress probing; `tools.ts` owns public tool definitions, argument validation, cwd resolution, temporary task-file creation, orchestration through `cmdRun()`/`cmdWait()`/`cmdApprove()`, and report truncation via `truncateReport()`. This is a strong boundary: the wrapper cannot access harness output except through returned tool text, and tool calls are allow-listable. The main concern is that `server.ts` currently contains a throwaway progress-probe branch controlled by `SONATA_MCP_PROGRESS_PROBE`; it is explicitly diagnostic, but it is transport behavior mixed into the production loop and should be removed or isolated once probing ends. `resolveToolCwd()` resolves relative paths against the server cwd and verifies directories, while the task temporary file is not cleaned up by `callTool()`, so temporary task lifecycle is a small ownership gap.

The adapter interface in `src/adapters/types.ts` is the extension boundary: `HarnessAdapter` requires `plan()`, approval capability/patterns, prompt description, key sequences, version metadata, and optional fallback report and health checks; `PlanInput` carries the generic launch context and `LaunchPlan` carries generated script plus interactivity/report-write capability. This keeps harness-specific knowledge out of the wrapper and mostly out of command code. The interface does, however, combine three concerns—launch compilation, interactive prompt protocol, and environment diagnostics—so adapters are both runtime backends and doctor providers. That is pragmatic for four backends, but a separate `HarnessHealth`/`HarnessInteraction` interface would reduce coupling as adapters grow. The `canWriteReport` field is particularly important but optional for backward compatibility; making the report capability explicit in a versioned plan contract would make false-success policy harder to misuse.

`src/adapters/opencode.ts` is the smallest adapter and demonstrates the non-interactive path. Its `buildScript()` maps read-only roles/plan to the `explore` agent and write-capable permissive modes to `build`, refuses write-capable `default` because OpenCode cannot ask for approval, and runs `opencode run` through `tee` before writing the exit sentinel; `canWriteReport` is false for read-only plans because the agent cannot be trusted to produce a report. Its `promptPatterns`, `describePrompt()`, and empty approval keys make the no-external-approval contract explicit, while `opencodeAdapter` supplies version and health metadata. Responsibility is split with `config.ts` (`isReadOnlyRole`) and `detect.ts` (model/auth probing), but that is consistent with the adapter boundary. The weaker enforcement of OpenCode’s read-only agent is an inherent backend limitation correctly surfaced as reporting semantics rather than hidden.

`src/adapters/pi.ts` owns Pi’s command construction and model-list parsing. `buildScript()` refuses write-capable `default`, passes `--no-context-files` because Sonata has already composed context, uses the combined provider/model id, and applies the real `--tools read,grep,find,ls` allow-list to read-only work; `parsePiRefs()` gates parsing on the table header and `countModelRows()` feeds `piHealth()`. The adapter marks read-only runs as unable to write reports, allowing tail’s terminal-output fallback. Pi has no approval UI, so `describePrompt()` returns null and approval keys are empty. The only notable split is that the generic read-only role rule is imported from config while the backend-specific tool allow-list remains here, which is the right direction; `detect.ts` still invokes Pi discovery directly but delegates parsing correctly.

`src/adapters/codex.ts` is the most complete backend integration. `parseCodexModels()` handles either JSON-RPC response shape and filters hidden/malformed models; `codexModelList()` performs bounded initialize/model-list JSON-RPC discovery; `buildScript()` maps plan/read-only roles to `codex exec` with read-only sandboxing, permissive modes to explicit sandbox policies, and `default` write work to an interactive TUI with `approval_policy="on-request"`; `interactiveScript()` waits for Sonata’s report then clears the composer and sends Ctrl-D; `configuredBaseUrl()`, `projectTrusted()`, and `codexHealth()` cover endpoint, trust, and authentication diagnostics. Prompt patterns and `describePrompt()` are fixture-driven, while `approveKeys` and `fallbackReportFile` define the external approval and report contracts. The adapter’s shell script owns interactive quitting that overlaps with Reasonix, and its health code owns policy/config parsing that could be shared as generic diagnostics utilities, but the harness-specific details rightly remain local. One subtle semantic boundary is that Codex’s `-o last-message.txt` is a harness fallback while the model report remains `report.md`; tail correctly prefers the model report and then adapter fallback.

`src/adapters/reasonix.ts` owns the most specialized TUI behavior and diagnostics. `permissionModeFor()` and `buildScript()` enforce `dontAsk` for read-only work, explicitly map accept-edits/bypass modes, and reserve interactive `ask` mode for default write runs; `headlessScript()` uses text output and `tee`, while `interactiveScript()` waits for the ready marker, types the task into the composer, watches for `report.md`, clears the line, and retries Ctrl-D until the exit sentinel appears. `parseReasonixRefs()` and `reasonixDoctorJson()` implement provider/model discovery, while `telemetryAnswered()` and `reasonixHealth()` detect first-run telemetry blocking, missing credentials, and inherited `.mcp.json` capability risks. `PROMPT_PATTERNS`, `describePrompt()`, and `approveKeys` encode the real approval-card protocol. The adapter has the same generic shell/quit overlap as Codex, plus an explicit acknowledged risk around stale pane prompts and composer state; consolidating interactive-run control would make this less fragile, but moving prompt regexes or Reasonix’s provider semantics out would violate the stated adapter boundary.

# BYOK (Bring Your Own Key) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let users configure native foreign-model agents with zero harnesses installed — pick a provider from the well-known list, fetch its model catalogue from the `/models` endpoint, enter an API key, and go.

**Architecture:** The well-known provider URLs (35+ entries in `src/detect.ts`) are already there. BYOK adds: (1) a model-fetcher that probes any OpenAI-compatible `/models` endpoint and returns a list, (2) a BYOK flow in the Ink wizard that shows well-known providers as selectable items alongside harness-discovered ones, (3) inline key entry when a selected provider has no key.

**Tech Stack:** TypeScript, Node built-in `fetch`, Ink React components (existing), vitest.

**Spec:** Approved design from conversation (2026-08-20): well-known provider picker + fetched model lists from `/models` endpoints + manual model ID fallback + inline key prompt. Works with zero harnesses.

**Revised 2026-08-21.** T2/T3 were written against the pre-Ink-rework wizard and
are restated below against the code as it stands. The deltas, each verified in
the source before rewriting:

- **The zero-harness case never reaches the wizard today.** `cmdInit` pushes a
  blocking `error` problem when `offered.length === 0` (`src/commands/init.ts:457`)
  and returns before the question sequence. BYOK's headline claim — works with no
  harness installed — is exactly this path, so the gate has to become conditional
  on BYOK being unavailable too, not merely skipped in the wizard.
- **There is no text input in the Ink app.** `src/tui-ink/components/` holds only
  `multi-select`. Inline key entry and the manual model-ID fallback both need a
  `TextInput` component that does not exist; it is now Task 2a.
- **`--key` is cut.** It contradicts this plan's own constraint that keys never
  appear in argv, where they land in shell history and `ps`. `sonata auth add
  <gateway>` already stores keys and is already what init's key-check step tells
  the user to run. The non-interactive path requires the key be stored first.
- **The key never crosses a process boundary.** `runInitTui` renders in-process
  and resolves with the object (`src/tui-ink/run.ts:17`), so `InitState.byokKeys`
  is memory only. It is written by `cmdInit` **after** the confirm gate — one
  write point, and cancelling stores nothing.
- **Fetched model ids need `isAnthropicRoutedName`.** Same defect class as the
  27-candidate filter shipped 2026-08-21: openrouter and friends serve `claude-*`
  ids that `parseConfig` refuses, so init could write a config it cannot read.

## Global Constraints

- Tests need no API keys and no network — the model fetcher is injected in tests.
- Keys never logged, never in conversation, never in argv, never rendered in the
  wizard summary — sonata's own store only.
- `sonata` on PATH runs `dist/` — `npm run build` before any live test.
- Run `npm test` and `npm run typecheck` before considering a task done.
- Also update `README.md` with BYOK documentation.

### Task 1: Model fetcher — probe `/models` endpoints

**Files:**
- Create: `src/native/models.ts`
- Test: `tests/native/models.test.ts`

**Interfaces:**
- Consumes: `WELL_KNOWN_PROVIDER_URLS` from `../detect.js` (exported in this task).
- Produces:
  ```ts
  export interface FetchedModel { id: string; name?: string }
  /** Probes an OpenAI-compatible /models endpoint and returns the model list.
   *  Returns [] on timeout/error — never throws. */
  export async function fetchModels(
    baseUrl: string,
    apiKey: string,
    opts?: { fetch?: typeof fetch; timeoutMs?: number },
  ): Promise<FetchedModel[]>

  /** The well-known provider list, exported for the wizard. */
  export function wellKnownProviders(): Array<{ name: string; url: string }>
  ```

- [x] **Step 3: Implement**

`fetchModels`: `fetch(baseUrl + '/models', { headers: { Authorization: 'Bearer ' + apiKey }, signal: AbortSignal.timeout(opts?.timeoutMs ?? 10000) })`, parse JSON, extract `data[].id` and optional `name`. Wrap in try/catch, return `[]` on any error.

`wellKnownProviders`: import `WELL_KNOWN_PROVIDER_URLS` (needs to be exported from `detect.ts`) and return `Object.entries(map).map(([name, url]) => ({ name, url }))`, deduped by URL, **keeping the first name for each URL** — the map is written openai-first, so keep-first is what makes the `openai` assertion hold; keep-last would yield `codex`.

Two traps in that map, both checked against `src/detect.ts:76-124`:
- `deep-infra` and `deepinfra` have **different** URLs (`/v1` vs `/v1/openai`). They look like aliases and are not — do not collapse them by name.
- Dedup by URL leaves 33 of the 37 entries, so the `> 30` assertion holds with little margin. Assert `>= 30`, not a fixed count, so adding a provider does not fail the test.

Drop `anthropic` from the returned list. Every model it serves is `claude-*`, which `isAnthropicRoutedName` refuses, so offering it produces a provider whose catalogue filters to empty — worse than not offering it.

Export `WELL_KNOWN_PROVIDER_URLS` from `src/detect.ts` (add `export` keyword).

### Task 2: BYOK providers in the Ink wizard

**Files:**
- Modify: `src/tui-ink/app.tsx`
- Modify: `src/tui-ink/app-state.ts`
- Modify: `src/tui-ink/types.ts`
- Modify: `src/commands/init.ts`
- Test: `tests/tui-ink/app-state.test.ts`

**Interfaces:**
- Consumes: `wellKnownProviders()`, `fetchModels()`, `byokCandidateKey()` (Task 1), `TextInput` (Task 2a), `resolveKeys` from `native/credentials.js`.
- Produces:
  ```ts
  // src/tui-ink/types.ts
  export interface InitState {
    // …existing fields unchanged…
    /** provider -> key typed in the wizard. In memory only; see below. */
    byokKeys?: Record<string, string>;
    /** provider -> model ids chosen or typed for that BYOK provider. */
    byokModels?: Record<string, string[]>;
  }
  // src/tui-ink/app.tsx
  export interface WizardData {
    // …existing fields unchanged…
    byokProviders: Array<{ name: string; url: string }>;
    /** Providers that already have a stored key, so the prompt is skipped. */
    keyedProviders: string[];
    /** Injected so tests never reach the network. */
    fetchModels?: typeof fetchModels;
  }
  ```

**Where the key lives.** `runInitTui` renders in-process and resolves with the
object (`src/tui-ink/run.ts:17`) — nothing is serialized — so `byokKeys` is
memory only, and `cmdInit` calls `writeSonataKey` **after** the confirm gate.
One write point, and a cancelled wizard stores nothing. Two consequences to
honour: `Summary` must not render `byokKeys`, and no `out()` line may include a
key.

**What changes:**

1. **A `byok` pseudo-harness, alongside the existing `config` one.** `cmdInit`
   already synthesises `{harness: 'config', key: 'config/<gateway>'}` entries for
   gateways no harness offers (`src/commands/init.ts:419-423`). BYOK providers
   follow that established shape: `{harness: 'byok', provider: name, key:
   'byok/<name>', count: 0}`. Reusing it means the provider picker, the
   non-interactive `--providers` validation, and `deriveInitState` all keep
   working unchanged rather than each growing a BYOK special case.

2. **`providersForHarnesses` must let them through.** It currently keeps a
   provider only if `harness === 'config'` or its harness is selected
   (`src/tui-ink/app-state.ts:48`); with no harness ticked, a `byok` entry would
   vanish from step 2. Add `byok` to that predicate.

3. **Offer only what is not already covered.** A `byok/<name>` entry is added
   only when no harness-discovered or config provider already has that
   `provider` name — otherwise deepseek appears twice, once with a catalogue and
   once without.

4. **Step 3 becomes two phases.** Phase one is the existing MultiSelect over
   `candidatesForProviders`, skipped when it would be empty (the zero-harness
   case). Phase two walks the selected `byok/` providers one at a time, indexed
   by a `byokIndex` state the way `roleIndex` already walks roles:
   a. **Key** — if the provider is not in `data.keyedProviders` and has no entry
      in `state.byokKeys`, show `TextInput` with `mask`, titled
      `API key for <name>`. Left goes back, esc cancels.
   b. **Fetch** — this is **the wizard's first async step**. Render a
      `fetching <name> models…` frame while a `useEffect` awaits
      `fetchModels(url, key)`; never block the reducer. Guard the state update
      with a mounted/aborted flag so a `←` during the fetch cannot write into an
      unmounted step.
   c. **Choose** — on a non-empty list, MultiSelect over the returned ids,
      filterable (catalogues run to hundreds).
   d. **Fallback** — on `[]`, `TextInput` titled
      `Model ids for <name> (comma-separated)`, split on commas and trim. State
      why: `could not reach <url> — enter ids by hand`. This is the path an
      offline machine and a non-OpenAI-shaped endpoint both take, so it must not
      read as an error.
   e. Ids matching `isAnthropicRoutedName` are dropped from both (c) and (d),
      with a line saying so. Openrouter's catalogue contains `claude-*` ids the
      router reserves; offering one lets init write a config `parseConfig`
      refuses — the defect fixed on 2026-08-21 for harness candidates, which
      would otherwise return through this new door.

5. **Selected BYOK models join `nativeKeys` immediately**, keyed by
   `byokCandidateKey(gateway, id)`. Step 5 (per-role models) lists
   `state.nativeKeys`, so a BYOK model that is not there cannot be assigned to a
   role. The key formula lives in `src/native/models.ts` and is imported by both
   the wizard and `cmdInit` — computing it twice is how the two disagree later.

- [x] **Step 1: Types** — add `byokKeys`/`byokModels` to `InitState`, and
  `byokProviders`/`keyedProviders`/`fetchModels` to `WizardData`.

- [x] **Step 2: `app-state.ts`** — add `byok` to `providersForHarnesses`, and an
  `applyStep` case recording `{provider, ids}` into both `byokModels` and
  `nativeKeys` (union, no duplicates).

### Task 3: BYOK candidates to native config

**Files:**
- Modify: `src/commands/init.ts`
- Modify: `src/cli.ts`
- Test: `tests/init.test.ts`

**Interfaces:**
- Consumes: `TuiResult.state.byokModels` / `.byokKeys`, `wellKnownProviders()`,
  `byokCandidateKey()`, `writeSonataKey`/`resolveKeys`.
- Produces: `InitOptions.providers` accepting `byok/<name>` keys. **No `--key`
  flag** — see the revision note.

**What changes:**

1. **The zero-harness blocker is downgraded.** `cmdInit` currently pushes a
   `severity: 'error'` problem when `offered.length === 0` and returns before the
   question sequence (`src/commands/init.ts:457-475`). With BYOK, having no
   harness is no longer fatal — it is the case this feature exists for. Make it a
   `warn` whose `fix` names BYOK, so the wizard still runs. Everything else about
   the blocking-error path stays: a missing tmux is still fatal.

2. **BYOK candidates.** For each `provider` in `state.byokModels`, for each id:
   `{key: byokCandidateKey(provider, id), gateway: provider, id,
   contextWindow: 128000, baseUrl: <well-known url>, auth: 'api-key'}`. Merge
   into `allNativeCandidates` before `nativeKeys` are resolved through
   `nativeByKey`, or every BYOK key resolves to `undefined` and is silently
   filtered out (`src/commands/init.ts:527`) — a wizard that appears to work and
   writes nothing.

3. **Keys are written after the confirm gate**, next to the config write:
   `for (const [gateway, key] of Object.entries(state.byokKeys ?? {})) writeSonataKey(opts.home, gateway, key)`.
   Print `✓ stored key for <gateway>` — the gateway name, never the key.

4. **Non-interactive path.** `--providers byok/<name>` plus `--models <id>…`
   works without a wizard and without a fetch: for a `byok/` provider, each
   `--models` entry is taken as a raw model id, because there is no local
   catalogue to validate against and a scripted path must not depend on the
   network. The key must already be stored — if `resolveKeys` reports none, throw
   naming `sonata auth add <gateway>` rather than writing a config that fails at
   first use.

## Self-Review

- **Spec coverage:** well-known picker (T2 item 3), fetched model lists (T1 +
  T2 item 4c), manual fallback (T2 item 4d), inline key (T2a + T2 item 4a),
  zero harnesses (T3 item 1 — the blocker downgrade, which is where that claim
  actually lives), README (T4). All covered.
- **Type consistency:** `FetchedModel` and `byokCandidateKey` from T1 are
  consumed in T2 and T3; `wellKnownProviders()` in T2 and T3; `byokKeys` and
  `byokModels` produced in T2, consumed in T3. `TextInput` from T2a is consumed
  only in T2.
- **Ordering:** T1 (fetcher) → T2a (input component) → T2 (wizard) → T3 (config
  writing + the zero-harness downgrade) → T4 (docs). Each is independently
  testable; T2a is separable because its reducer is tested without a TTY.
- **Deliberately not built:** `--key`. It contradicts the constraint that keys
  never enter argv, and `sonata auth add` already covers the case.
